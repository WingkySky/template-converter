# 多列金额拆分发放（拆行）设计

日期：2026-10-15 · 状态：已与用户逐节确认（brainstorming 产出）

## 1. 背景与目标

客户发放费用常被拆分到多列——真实样例（2026-10-12 微信明细截图）中「第一笔」「第二笔」
两列拆分金额，另有「代扣缴后」总额列（= 两笔之和）。导出管线全程假设**单金额列**
（`row[typeToCol.amount]`），现状多列标记时后标覆盖先标、金额被静默丢弃。

目标：用户显式标记多列税前金额（及合计列）后，确认映射时**自动拆行**——同一行内每个
非空拆分列生成一行同名要素（姓名/身份证/卡号/银行/电话）的发放记录，规范化输出。

### 已确认的关键决策（2026-10-15 与用户逐项确认）

1. **拆分列/合计列由用户显式标记**：列映射下拉把多列都标成「税前金额」；新增类型
   「合计金额（仅核对，不导出）」标总额列。不做自动判断——发钱场景误判一列即重复发放。
2. **空金额（含 0）跳过不生成**；全部拆分列都空的行保留原行 1 行。
3. **备注列写来源列头**（「第一笔」「第二笔」）；源表无备注列时行尾追加虚拟备注列；
   已有备注追加不覆盖（`原备注；第一笔`）；目标模板无备注列则静默跳过。
4. **合计自动核对在确认映射前完成**：预览阶段逐行核对「拆分金额之和 = 合计列值」标红，
   确认时仍不平则弹窗列出、可选择返回修改（数据不静默带病下发）。
5. **方案 A：确认映射时拆行 + 金额归一**到最左拆分列（即 `typeToCol.amount`），
   模板生成/KB 匹配/备注面板/导出预览零改动。

### 非目标（本期不做）

- 跨行同名合并/去重（同名多行本就独立发放）
- 合计列自动判断（某列=其余之和的启发式）
- 非预览数据源的多列拆分（自动识别本就只标一列金额；多源合并中未预览源维持现状）
- 独立「拆分向导」步骤

## 2. 交互设计

- 列映射下拉：**「税前金额」可标多列**（修复现状后标覆盖先标）；新增下拉项
  「合计金额（仅核对，不导出）」。
- 统计条实时提示：多列税前金额时显示「确认后将按拆分列展开为 M 行发放记录（跳过空金额）」
  （M = ∑ 各原始行非空拆分列数，全空行计 1）；标了合计列则追加合计核对结果，不平的行
  逐条标红（`第 X 行拆分合计 39315.71 ≠ 合计 39315.70`，X 为原始行在有效数据中的序号，
  非拆行后序号）。
- 确认映射：核对不平 → confirm 弹窗列出问题行，可返回修改或仍要继续。
- 最终拆行结果在**导出预览**完整可见（每行备注带来源标签）——所见即所得的最终关卡。

## 3. 拆行规则（确认映射时，按数据源独立执行）

1. 收集所有标记为税前金额的列（按列序升序），最左列 = 归一目标列（`typeToCol.amount`）。
2. 每个原始行：非空且非 0 的拆分列有几个就生成几行——每行把对应金额写进归一列、
   其余拆分列清空；全部拆分列空 → 保留原行 1 行（金额空交给下游过滤逻辑）。
3. 同名要素列逐行原样复制；跨行同名不做合并。
4. 备注来源标注：见关键决策 3。
5. 合计核对：`sum(非空拆分列) vs 合计列值`，容差 `max(0.02, |合计|×1e-6)`。

## 4. 技术设计

- **`src/core/mapping/row-expand.ts`（新增，纯函数）**：
  `expandAmountSplitRows(dataRows, { amountCols, totalCol?, noteCol?, labelOf })`
  → `{ rows, noteCol, mismatches: [{ rowIndex, sum, declared }] }`
  - `amountCols.length ≤ 1` → **返回原数据引用**（单金额列场景字节级不变，compare 基线零变化）；
  - 金额解析复用 `core/mapping/amount-score` 的 `isAmountLikeNumber` 体系（兼容千分位）；
  - 虚拟备注列：`noteCol` 为空时所有行（含未拆行行）行尾对齐追加，返回实际 noteCol。
    这保证**源侧**总能提供备注值；若目标模板本身没有备注列，导出时该值自然被忽略。
- **`column-detect.ts`**：`COL_TYPE_LABELS` 新增 `'amountTotal': '合计金额（仅核对，不导出）'`；
  自动识别（detectColumnMapping）**永不标该类型**（纯手动），基线不受影响。
- **`confirmMapping`（mapping.ts）**：typeToCol 构建改为收集全部税前金额列（升序，
  `typeToCol.amount` = 最左，其余拆分列不进 typeToCol）；`amountCols ≥ 2` 时调拆行并
  写回 `typeToCol.note = 返回的 noteCol`；核对不平 → confirm 弹窗（返回修改 / 仍要继续）。
- **`showMappingStep`**：dry-run 同一纯函数渲染统计条（预估行数 + 合计核对明细）。
- **导出面零改动**：export.ts / 备注面板 / KB 匹配看到的已是拆行后规范单金额行；
  `amountTotal` 不进 typeToCol 导出面，自定义映射 UI 不受影响。

## 5. 边界与风险

| 项 | 处理 |
|---|---|
| 单金额列 | 行为与现状完全一致（返回原引用，compare 零变化硬门槛） |
| 0 元/空/不可解析金额 | 一律视同空跳过 |
| 全部拆分列为空的行 | 保留原行 1 行 |
| 虚拟备注列与既有列序 | 追加在行尾，所有行对齐补齐；colIndex 按类型查找不受影响 |
| 拆行后行数膨胀 | 导出预览已有 previewRowLimit 增量机制；统计条提前预告行数 |
| 备注 panel / KB 匹配行索引 | 均基于拆行后数据运作，天然一致 |
| 图片源 | 拆行前已完成清洗/校验/姓名推断，顺序不受影响 |
| 合计核对容差 | `max(0.02, |declared|×1e-6)`，浮点累加误差不误报 |

## 6. 测试与验收

- **单测（vitest）**：row-expand 全规则矩阵——多列拆行（样例数据：王辉 2 行、王辉2 跳空 1 行）、
  金额归一与清空、备注追加/虚拟列、合计核对收集、单列返回原引用、0 元跳过、全空保留。
- **compare 红线**：208 产物零变化（基线均为单金额列）。
- **浏览器验收**：真实样张截图（图片源，第一笔/第二笔）+ 合成 CSV 各一遍——
  核对拆分后行数（样例应为 12 人 → 21 行）、备注来源标签、合计核对报错路径。

## 7. 实施记录（2026-10-15 当日实施完成）

- `row-expand.ts` 7 项单测全绿；`amountTotal` 类型仅入 COL_TYPE_LABELS（detect 不自动标）；
  confirmMapping 多列收集/拆行/核对弹窗、showMappingStep dry-run 预警全部落地。
- 质量门：typecheck ✓ · 382 测试全绿 ✓ · compare 208 产物零变化 ✓ · build:single ✓。
- **实施中发现并修复一个真 bug**：onMapChange 改为实时重渲染后，showMappingStep 的
  重新自动检测会**冲掉用户在下拉中的手动标注**——已加「同源按列号回填用户类型」合并
  （切换预览源不串、用户标注优先于自动检测），浏览器实测三列标注跨三次重渲染全部保留。
- 浏览器端到端（合成 CSV：5 人/两笔拆分/故意 1 行合计不平）：预警条实时显示
  「展开为 7 行；合计核对 1 行不平（第 5 行 1000≠999）」→ confirm 弹窗 → accept →
  导出预览 7 行（金额归一、要素复制、姓名清洗王辉2→王辉、备注全部带「第一笔/第二笔」）。
  注：备注列在预览中是 `<input>`，排查时用 textContent 探测会误报为空——用 input.value 验证。
