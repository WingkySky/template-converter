# 多列金额自动识别（求和关系仲裁）设计

日期：2026-11-09 · 状态：已与用户确认方案（brainstorming 产出）

## 1. 背景与问题

2026-10-15 上线的「多列金额拆分发放」（`docs/superpowers/specs/2026-10-15-amount-split-rows-design.md`）
要求用户在映射页把 ≥2 列手动标为「税前金额」才触发拆行。用户实测（2026-11-09「26年10月天九分润」表，
表头 `姓名|税后|第一笔|第二笔|账号|银行|身份证|电话|是否认证`）发现功能"没反应"：

- `detectColumnMapping`（`src/core/mapping/column-detect.ts` L110-127）**最多只认领 1 列 amount**；
- 本表实测：`税后 → amount`、`第一笔/第二笔 → 未识别`，amount 列数 = 1 < 2，
  预警条与 confirmMapping 拆行均不触发。

原设计决策 1 曾明确"不做自动判断——发钱场景误判一列即重复发放"，并把"合计列自动判断"列入非目标。
本次用户确认演进为自动识别，前提是误判风险必须有兜底（见 §5）。

## 2. 用户需求（2026-11-09 逐项确认）

- 拆分列形式需覆盖：**第N笔式**（第一笔/第二笔）、**月份/期间式**（1月/2月…）、
  **项目名式**（劳务费/代缴费等，表头看不出拆分语义）→ 统一靠**数据求和关系**通用识别，
  表头模式仅作兜底信号。
- 目标行为（以天九分润表为例）：导入后自动变为
  `税后 → 合计金额（仅核对，不导出）`、`第一笔/第二笔 → 税前金额`，
  映射页自动出现「检测到 2 列税前金额，确认后将展开为 N 行发放记录」提示，确认即拆行，零手动标注。

## 3. 检测算法

改造 `src/core/mapping/column-detect.ts` 的 `detectColumnMapping`：在关键词认领之后、
现有单列 amount 认领之前插入「多列金额仲裁」阶段。

### 3.1 候选列收集

- 范围：未被关键词认领的列；
- 门槛：金额样占比 ≥ 0.6（复用 `isAmountLikeNumber`，取前 12 个非空样本）；
- 排除：表头命中排除正则（现有排除表追加 `数量|件数|笔数|人数|天数`）；
- 上限：候选 ≥ 2 且 ≤ 8 才进入多列仲裁（求和验证要求 ≥ 3 = 1 合计 + ≥2 拆分；
  表头模式兜底允许 = 2；候选 < 2 或 > 8 直接走原单列逻辑）。

### 3.2 求和验证

- 枚举「合计列 c + 拆分子集 S」组合：`c ∈ 候选`，`S ⊆ 候选\{c}` 且 `|S| ≥ 2`（全子集枚举，≤ 2^7 × 8 组合）；
- 行级判据：`|sum(S) − row[c]| ≤ max(0.02, |row[c]| × 1e-6)`（与 row-expand 合计核对同一容差）；
- 两段验证：先用前 20 行，命中率 ≥ 80% 再全量复核仍 ≥ 80% 才算命中；
- 多个命中取**拆分列数最多**者；并列取合计列命中行数最多者；再并列取列序靠左者。

### 3.3 认领结果

- 命中：合计列 → `amountTotal`，S 中每列 → `amount`；跳过现有单列 amount 认领；
- 未命中但表头呈拆分模式（`第[一二三…\d]+笔` 或同前缀月份序列）且候选 ≥ 2：
  全部候选标 `amount`（无合计列，合计核对自然跳过）；
- 未命中且无表头模式：完全走现有单列 amount 逻辑（评分最高/备用数据判定），行为与现状一致。

### 3.4 红线

候选不足或仲裁未命中时，检测结果与现状**逐字节一致**——单金额列场景 compare 基线零变化。

## 4. UI / 拆分管线联动（零改动）

- `mapping.ts` 的 `amountColsSel` / `totalColSel` 从 `autoMap.cols` 读取，多列认领后
  预警条（「检测到 N 列税前金额…」）与合计核对提示自动出现；
- `confirmMapping` 的 `expandAmountSplitRows` 拆行逻辑照旧，无需改动；
- 用户手动改下拉框仍可覆盖（`applyUserTypeOverrides` 用户优先逻辑不变）。

## 5. 误判防护与发钱兜底

1. 求和验证双门槛：金额样占比 ≥ 0.6 + 行级求和命中率 ≥ 80%（前 20 行粗筛 + 全量复核）；
2. 序号/数量列被排除正则或凑不出求和关系双重挡住；卡号/身份证列已被关键词认领挡在候选外；
3. **最终兜底**：即使识别错列，confirmMapping 拆行时的合计核对不平会弹窗列出
   （`拆分合计 X ≠ 合计 Y`），用户可返回修正——数据绝不静默带病下发（沿用 2026-10-15 设计）。

## 6. 测试计划

- 扩展 `tests/unit/mapping/column-detect.test.ts`：
  - 第N笔式（用天九分润表真实数据：税后=第一笔+第二笔）→ amountTotal + 2×amount；
  - 月份式（1月/2月 + 合计列）；
  - 项目名式（劳务费/代缴费 + 总计列）；
  - 无求和关系 → 回退单列认领，与现状一致；
  - 序号列/数量列不误判；部分行空拆分列仍命中；
  - 候选 <3 / >8 直接走原逻辑。
- 回归：`tests/tools/compare.mjs` 全量基线对比；若某 fixture 触发多列仲裁导致基线变化，
  逐个人工确认行为正确后更新基线并说明。

## 7. 非目标

- 映射页「整理表」直接导出不拆行（2026-10-14 设计既定，不动）；
- 不改 `row-expand.ts` / `confirmMapping` / 拆分导出管线；
- 不做跨表（多源）联合求和判断——仲裁按数据源独立执行（detect 本就按 sheet 独立调用）。
